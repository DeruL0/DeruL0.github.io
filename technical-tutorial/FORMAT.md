# 固定叙事式章节格式

从第 1 日修订版开始，每篇教程采用下面八段固定结构。固定的是阅读路径，不是关键词栏目。

一篇章节必须让读者沿着同一条因果链走完：

```text
现实任务
→ 最初的做法
→ 做法暴露的问题
→ 为解决问题引入的新抽象
→ 数学或系统模型
→ 从输入到输出的完整过程
→ 工程中的具体落点
→ 已经得到什么、下一步为什么出现
```

## 1. 从一个真实任务开始

先描述这项技术最初究竟要完成什么工作。必须给出对象、输入、输出和使用场景，让读者知道“为什么需要这一章”。

这一部分不提前堆公式，也不假设读者已经接受作者的抽象。

## 2. 最直接的办法，以及它为什么不够

从符合直觉的朴素方法开始。通过具体例子展示它在哪一步失败。新的概念必须作为解决该失败的需要而出现，不能突然定义。

## 3. 关键想法是怎样被引出来的

解释从失败现象到关键抽象之间的推理。回答：

- 我们观察到了什么结构？
- 为什么这个结构值得单独命名？
- 它排除了哪些错误方向？

## 4. 一步一步建立正式模型

按推理顺序引入变量和公式。每个公式出现前先说明它要表达什么，出现后再解释结果的含义。

禁止连续给出一组未解释的定义。

## 5. 跟着一个完整例子走到底

使用一组连续输入，从第一步计算到最终输出。例子中间不能跳过恰好最难理解的步骤。

## 6. 回到真实系统：程序实际上怎样工作

说明数据结构、模块、执行顺序、正确性条件和性能因素。工程内容必须和前面的模型逐项对应。

## 7. 容易走错的岔路

不只是列出误区，还要说明错误理解为什么看似合理，以及它在哪种情况下暴露。

## 8. 本章落点、验证与下一章

用连贯文字回答：

- 本章最终解决了什么？
- 它映射到用户项目的哪个位置？
- 用什么 30 到 90 分钟练习确认理解？
- 下一章的问题为什么会自然出现？

## 写作约束

- 每篇必须是连续讲解，不得写成术语清单或论文清单。
- 标题下应以完整段落为主；列表只用于确实需要并列的信息。
- 图和公式必须服务于当前推理，并在正文中解释。
- 研究工作只能放在基本问题讲清之后，用于说明哪个假设正在被修改。
- 练习只能验证已经讲过的知识，不能要求读者先自行研究核心内容。
- 五条线保持独立，不为了“综合项目”强行混合。

# CT：工业 CT 系统集成、验收与可追溯验证

## 1. 从一个真实任务开始

今天的 CT 任务不是再写一个更漂亮的重建算法，而是把一套工业 CT 检测流程交给生产线使用。客户给你的零件可能是增材制造金属件、复合材料接头、微孔结构样品，或者带有内部油道的铸件。真正的交付物不是一张三维图，而是一条可重复执行的链：操作者放入零件，系统按固定 recipe 扫描，软件完成校正和重建，测量模块给出壁厚、孔隙率、缺陷尺寸或几何偏差，最后报告要能回答“这个零件是否合格”，并且在几个月后仍能追溯这次判断从哪里来。

这件事在知识树里位于“采集物理、测量模型、重建算法”之后。前面章节已经解释了 X 射线通过物体后如何变成 detector counts，counts 如何经由 Beer-Lambert 模型进入投影数据，投影数据又如何约束体素衰减系数。今天往前走一步：工业系统不只要估计一个体数据，还要证明这个估计足够稳定、足够可追溯，可以支持某个具体质量决策。ASTM 关于 CT 系统性能测量的标准实践，例如 [ASTM E1695](https://www.astm.org/e1695-20.html)，以及 NIST 对 X-ray CT 尺寸测量可追溯性的讨论，强调的正是这个层面：图像质量指标、空间分辨率、对比灵敏度、尺寸测量链路和不确定度必须被制度化，而不是凭一次好看的重建结果说服自己。

## 2. 最直接的办法，以及它为什么不够

最直接的做法很诱人：你选一个曝光时间、管电压、投影数和重建参数，扫一件样品，调到视觉上清楚，然后把脚本保存起来。下次遇到同类零件，就用同一个脚本跑。这个办法在研究 demo 中经常有效，因为研究 demo 的目标是证明方法能在某个数据集上工作；但在工业环境里，它很快会失败。

失败的原因不是“算法不好”，而是系统输入在悄悄变化。X 射线源的焦点会漂移，detector 的坏点和暗电流会变化，旋转台的几何中心可能有微小偏移，操作员可能更换滤波片，软件版本可能改了 beam hardening correction，甚至同一零件在夹具中的姿态也可能改变。更重要的是，客户并不只问“图像看起来对不对”，而是问“这次报告的 1.040 mm 壁厚能否可靠地区分 1.05 mm 的上限”。如果系统没有保存 scan recipe、校准状态、几何参数、重建版本、分割规则和测量不确定度，那么一个结果即使数值正确，也不能被稳定地验收。

## 3. 关键想法是怎样被引出来的

从这个失败中自然引出的关键抽象叫验证契约，也可以理解为一条可追溯的测量链。研究算法通常把重建结果写成 `volume = R(projections)`，好像 projections 是唯一输入；工业系统必须把结果写成“在某个采集协议、几何校准、校正状态、软件版本和报告规则下产生的测量值”。也就是说，CT 结果不是单一算法输出，而是一个受控系统输出。

这个抽象的意义是把“是否可信”从主观判断变成可检查条件。一次测量值只有在这些条件都成立时才有效：原始 counts 经过了正确的 dark/flat correction；扫描几何与校准记录一致；phantom 或 reference artifact 的性能检查通过；重建软件和参数有版本标识；分割和测量规则被固定；报告中的每个任务指标都有不确定度或至少有经验误差界。这样，系统集成不再是把模块串起来，而是定义每个模块向下游承诺什么、下游又如何验证这个承诺没有失效。

## 4. 一步一步建立正式模型

先从物理端开始。Detector 第 `i` 个像素记录到的不是连续理想强度，而是有噪声的计数。给定物体的线性衰减分布 `x`、扫描几何 `g` 和扫描协议 `s`，可以把计数写成一个 Poisson 观测：

\[
n_i \sim \mathrm{Poisson}(\lambda_i(x,g,s)).
\]

这个式子的重点不是 Poisson 本身，而是它把三个容易被忽略的输入放回了模型：被测对象 `x`、几何 `g`、扫描协议 `s`。如果几何或协议改变，`n_i` 的统计意义也改变，后面的重建不能假装自己拿到的是同一类数据。

接下来，重建软件把 counts、几何和协议转换成体数据：

\[
\hat{x}=R_\theta(n,g,s).
\]

这里的 `theta` 表示软件版本、重建参数、校正模型和实现细节。把 `theta` 写出来，是为了提醒自己：算法升级会改变测量链。一次工业验收不能只记录“用了 FDK”或“用了 iterative reconstruction”，还要记录滤波器、体素尺寸、中心校正、beam hardening correction、ring artifact correction 和阈值策略。

最后，报告模块并不直接输出整幅体数据，而是输出某个任务测量：

\[
m=Q(\hat{x},r),
\]

其中 `r` 是报告规则，例如壁厚测量的位置、分割阈值、孔隙连通性定义、缺陷等效直径定义。工业 CT 的验收要面对的问题是：`m` 附近的不确定度有多大。一个简化的不确定度预算可以写成

\[
u_c^2(m)=\sum_k \left(\frac{\partial m}{\partial z_k}\right)^2u^2(z_k),
\]

其中 `z_k` 是影响测量的因素，例如尺度校准、重复扫描、分割阈值、几何中心、噪声水平。这个式子并不是要求你真的每次都解析求导，而是要求系统工程上明确：报告值不是孤立数字，它来自多个误差源的传播。常见验收会使用扩展不确定度

\[
U=k u_c,
\]

例如取 `k=2` 表示近似 95% 覆盖范围。于是合格判断不再是 `m` 是否落在公差内，而是 `m \pm U` 与公差区间的关系。

## 5. 跟着一个完整例子走到底

假设今天要验收一个内部通道的最小壁厚。图纸要求壁厚必须在 0.95 mm 到 1.05 mm 之间。CT 系统扫描后，重建和分割模块给出某个关键位置的壁厚：

\[
m=1.040 \text{ mm}.
\]

如果只看这个数字，结果似乎合格，因为 1.040 小于上限 1.05，也大于下限 0.95。可是工业报告不能停在这里。你把系统中已知的主要不确定度分量列出来：尺度校准带来 0.015 mm，重复扫描带来 0.010 mm，分割阈值带来 0.020 mm，几何中心残差带来 0.012 mm。为了先建立可解释流程，暂时假设它们近似独立，则合成标准不确定度为

\[
u_c=\sqrt{0.015^2+0.010^2+0.020^2+0.012^2}=0.0295 \text{ mm}.
\]

取覆盖因子 `k=2`，扩展不确定度为

\[
U=2u_c=0.059 \text{ mm}.
\]

所以这次报告真正能支持的区间是

\[
[m-U,m+U]=[0.981,1.099]\text{ mm}.
\]

这个区间跨过了 1.05 mm 上限。结论不是“零件一定不合格”，而是“在当前扫描和测量链下，无法以这个不确定度声明它满足上限要求”。这就是系统验证和视觉重建的差别：一张清晰图像可能让人觉得 1.040 mm 很可靠，但验收链会告诉你，当前 protocol 对这个公差太松，或者分割规则太敏感，或者必须换更高分辨率、更高投影数、更稳定的夹具，才能把不确定度压到能做合格判定的范围。

## 6. 回到真实系统：程序实际上怎样工作

在真实工程里，这个验证契约应当变成数据结构和自动检查。采集模块保存 source voltage/current、exposure、filter、projection count、detector binning、dark/flat frame id、fixture id 和 operator id。几何模块保存 source-detector distance、source-object distance、rotation axis offset、detector tilt、体素尺寸和校准时间。重建模块保存代码版本、参数文件 hash、GPU kernel 版本和输出体数据 hash。测量模块保存分割规则、测量 ROI、surface extraction 参数和报告模板版本。

对你的 CT Framework 或 CTGS 项目来说，这意味着原型不应只有 `volume.npy` 或一组训练好的 Gaussian。每次实验都应该有一个 artifact bundle：原始或校正后的 projection、geometry JSON、reconstruction config、training config、checkpoint、validation report 和最终任务指标。工业 CT 中的 phantom scan 可以作为 release gate：只有当空间分辨率、噪声、对比灵敏度、尺度误差和重复性都在阈值内，才允许把这次软件版本用于正式报告。NIST 对 CT 尺寸测量可追溯性的讨论可以作为你设计这类 gate 的参考，因为它把 CT 从“成像设备”拉回到“测量系统”。

如果你把 CTGS 当作 CT reconstruction 的可训练表示，那么这条链更重要。训练 loss 下降并不等于测量可信；你还要保存训练使用了哪些投影、哪些投影被留作验证、geometry 是否固定、Gaussian densification 是否改变了任务测量、最终报告是否能追溯到原始 counts。否则 CTGS 很容易变成一个视觉上锐利、任务上不可验收的重建器。

## 7. 容易走错的岔路

第一个岔路是用视觉质量替代验收质量。CT 图像看起来清楚，只能说明某些结构可见；它不能自动说明壁厚、孔隙率或缺陷尺寸在指定公差内可靠。第二个岔路是只保存重建结果，不保存采集和校准上下文。这样做会让后续误差分析几乎不可能，因为你不知道结果变化来自样品、扫描、校正还是软件。

第三个岔路是“一次校准永久有效”。工业设备会漂移，detector 会老化，机械轴会有变化。校准不是一个历史事件，而是一组有有效期的系统状态。第四个岔路是把算法升级和扫描 protocol 改动混在同一次实验里，然后用结果改善证明某个模块有效。工业系统需要受控 A/B：如果改的是重建算法，就保持扫描、几何、报告规则不变；如果改的是扫描协议，就保持重建和测量规则不变。否则你无法把性能变化归因。

## 8. 本章落点、验证与下一章

今天的落点是：工业 CT 的核心交付不是漂亮体数据，而是带有可追溯上下文和不确定度意识的测量系统。采集任务产生 counts，counts 依赖几何和 protocol，重建依赖软件和校正，报告依赖分割和任务规则；验收要检查整条链，而不是只检查最后一张图。

验证练习用 60 到 90 分钟完成：选你现有 CT 或 CTGS 项目中的一个任务指标，例如壁厚、孔隙率、缺陷体积或表面偏差，写一个 `measurement_contract.md`。里面必须包含原始数据来源、geometry 文件、重建或训练配置、测量规则、至少四个不确定度来源，以及一个像本章例子那样的 `m ± U` 公差判断。预期结果是你能明确说出：这个指标目前能不能被验收，如果不能，最大的不确定度来源是哪一个。

下一章自然会进入“把验证契约变成自动化 benchmark 和 release gate”。因为只知道要保存什么还不够，真正的系统需要在每次代码、参数或设备状态变化后自动告诉你：这次变化是否破坏了 CT 测量链。

# 几何处理：高性能几何内核、空间索引与并行遍历

## 1. 从一个真实任务开始

今天的几何任务是处理一个来自工业 CT 或高精度扫描的巨大三角网格。它可能有 5000 万到 1 亿个三角形，你要在上面做最近点查询、射线相交、自交检测、局部厚度估计、Boolean 预处理，或者把 STL 表面和 CT 体数据对齐。前面章节已经讲过网格、离散曲率、Laplacian、谱分解和形状优化；这些知识告诉你什么计算是对的。今天的问题变成：当计算规模上来之后，怎样让这些正确的几何操作在真实系统里跑得动。

这章在知识树中属于“几何算法到几何内核”的过渡。算法课常常关心单个操作的数学定义，例如点到三角形距离、ray-triangle intersection、cotangent Laplacian。几何内核关心的是另一层问题：数据怎么放，谓词怎么保证稳健，空间索引怎么剪枝，遍历怎样批量化，输出怎样并行压缩，哪些地方用成熟库，哪些地方写专用 kernel。CGAL、libigl 和 Embree 分别代表了这条线上的不同取向：CGAL 重视稳健几何和精确谓词，libigl 重视研究原型中的矩阵化几何处理，Embree 则把高性能 ray tracing 内核做到了工程级别。

## 2. 最直接的办法，以及它为什么不够

最直接的做法是为每个查询遍历所有三角形。你有一个点 `p`，要找最近三角形，就计算它到每个 triangle 的距离，取最小值。你有一条射线，要找交点，就测试它和每个 triangle 是否相交。这个做法非常容易实现，而且在几千个三角形时完全可以接受。

失败发生在规模和重复查询同时出现的时候。假设网格有 100 万个三角形，查询点有 10 万个。直接方法需要

\[
10^6 \times 10^5 = 10^{11}
\]

次 triangle test。即使每次测试只花几十纳秒，总时间也会变成无法接受的数量级。更糟的是，朴素数据结构通常是 pointer-heavy 的半边结构或面对象数组，CPU cache miss 很多；在 GPU 上，线程会因为不同查询走不同分支而发散；如果每个命中结果都用 atomic 追加到数组，输出阶段又会成为瓶颈。

## 3. 关键想法是怎样被引出来的

从这个失败中引出的关键抽象是几何内核，而不是单一几何算法。几何内核可以看成四件事的组合：紧凑的数据布局、可分层剪枝的空间索引、足够稳健的几何谓词，以及适合 CPU SIMD 或 GPU wavefront 的批量遍历方式。换句话说，高性能不是把一个 `for triangle in mesh` 写得更快，而是避免绝大多数 triangle test，并让剩下的 test 按硬件喜欢的方式发生。

空间索引的核心思想是用一个粗包围体先代表一组三角形。若查询点到这个包围体的最小可能距离已经大于当前最优距离，那么包围体内部的所有三角形都不可能成为答案，可以整块跳过。射线查询也是类似：如果 ray 不穿过某个 bounding box，就不需要测试里面的 triangles。这样，计算从“查询与所有 primitive 的关系”变成“查询与层级节点的关系”，几何问题被改写成可剪枝的搜索问题。

## 4. 一步一步建立正式模型

先定义直接方法的代价。若三角形数为 `N`，查询数为 `Q`，每个查询遍历整个 mesh，则复杂度近似是

\[
O(QN).
\]

这不是抽象上的坏，而是工程上灾难性地坏，因为 `Q` 和 `N` 在 CT mesh、STL 修复和 surface fitting 中都会很大。空间索引把 mesh 组织成一棵 BVH 或 AABB tree。每个节点 `B` 包含一组 primitives 的 axis-aligned bounding box。对最近点查询，我们先计算点 `p` 到 box 的距离下界：

\[
d_B^2(p)=\sum_{a\in\{x,y,z\}}
\begin{cases}
(B_{\min,a}-p_a)^2, & p_a<B_{\min,a},\\
0, & B_{\min,a}\le p_a\le B_{\max,a},\\
(p_a-B_{\max,a})^2, & p_a>B_{\max,a}.
\end{cases}
\]

这个式子只是把一维区间距离在三个轴上相加。它重要的地方在于提供了安全剪枝规则：如果当前已经找到的最近距离是 `d_best`，并且

\[
d_B^2(p)>d_{\mathrm{best}}^2,
\]

那么节点 `B` 内部所有三角形都不可能更近，可以不访问。对于射线查询，AABB test 给出 ray 进入和离开 box 的参数区间；若区间为空，就剪掉这个节点。

高性能内核还要处理输出。许多几何算法先产生一个布尔标记，例如哪些 triangle 与局部 box 相交，哪些点需要重新投影，哪些 faces 需要进入下一轮修复。并行程序不能让所有线程随意 push 到同一个数组，而是先计算 flag：

\[
f_i\in\{0,1\},
\]

再用 prefix sum 得到输出位置：

\[
o_i=\sum_{j<i}f_j.
\]

这样每个有效元素 `i` 都知道自己应该写到 `o_i`，输出阶段从竞争写入变成无冲突写入。这个小模型经常决定一个几何算法能不能从单线程 demo 变成 GPU 或多核可用实现。

## 5. 跟着一个完整例子走到底

假设你有一个 100 万三角形的 CT 表面 mesh，要把 10 万个采样点投影到最近表面。直接方法需要 `10^11` 次点到三角形距离测试。现在构建一个 BVH。理想平衡树的深度大约是

\[
\log_2(10^6)\approx 20.
\]

真实 BVH 不是每个查询只访问 20 个节点，因为最近点查询会访问若干相邻分支。假设平均每个查询访问 60 个 box，并最终测试 8 个候选三角形，则总测试量大约是

\[
10^5\times(60+8)=6.8\times10^6.
\]

这和 `10^11` 的差距不是常数优化，而是问题形态被改变了。它也解释了为什么很多几何处理系统宁愿花时间 build BVH：只要后续查询足够多，索引成本会被摊薄。

再看输出压缩。假设一次局部修复中，五个三角形的有效标记是

\[
f=[1,0,1,1,0].
\]

exclusive prefix sum 给出

\[
o=[0,1,1,2,3].
\]

只有 `f_i=1` 的元素写出，所以 triangle 0 写到输出 0，triangle 2 写到输出 1，triangle 3 写到输出 2。压缩后的索引是 `[0,2,3]`。这个例子很小，但它就是 GPU mesh processing 中大量 stream compaction、active set update 和 collision pair filtering 的基本形态。

## 6. 回到真实系统：程序实际上怎样工作

在你的几何线项目里，合理做法通常不是从零写一个全能几何库。研究阶段可以用 libigl 快速表达 Laplacian、mass matrix、harmonic field、mesh smoothing 和 parameterization，因为它把许多几何操作自然落到稀疏矩阵和数组上。需要鲁棒 Boolean、精确相交和复杂拓扑时，应优先评估 CGAL 这类成熟库，因为浮点谓词在退化三角形、共面相交和近重合边界上很容易出错。需要大量 ray 或 closest-hit 风格查询时，Embree 的 BVH 和 SIMD 遍历非常值得作为 CPU 高性能基线。

如果你自己写内核，重点应放在项目特有的热路径上。例如 CT STL 到体数据的距离场、局部壁厚查询、点云到网格投影、或者 DirectX viewer 中的 picking 和 collision。这里更适合使用结构化数组布局，例如把 vertex position 分成连续的 `x/y/z` float arrays 或压紧的 triangle vertex buffer，减少 pointer chasing。对于 GPU，最好把 traversal、candidate generation、predicate evaluation 和 output compaction 拆成清晰阶段，避免一个 kernel 同时做复杂树遍历、动态分配和全局 atomic append。

## 7. 容易走错的岔路

第一个岔路是以为“有 BVH 就一定快”。BVH 的质量、构建方式、内存布局和查询分布都会影响性能。一个 badly built BVH 可能导致大量节点重叠，查询时仍然访问很多分支。第二个岔路是每次小改 mesh 都重建完整索引。如果 mesh 只是局部变化，可能需要 refit；如果 topology 大改，才需要 rebuild。把这两种情况混在一起，会让系统浪费大量时间。

第三个岔路是把精确谓词放进所有 hot path。稳健性很重要，但工业级性能常用两层策略：普通情况走快速浮点谓词，接近退化或符号不确定时再走 exact fallback。第四个岔路是输出阶段依赖 atomic push。少量命中时 atomic 可以接受；大量候选 pair 或 active elements 时，prefix sum compaction 通常更稳定、更可预测。

## 8. 本章落点、验证与下一章

今天的落点是：几何处理进入大规模系统后，核心对象从“单个几何公式”变成“几何内核”。一个合格内核必须同时回答数据如何连续存放、空间索引如何剪枝、谓词如何处理退化、遍历如何批量化、输出如何压缩。否则算法在小模型上正确，在 CT mesh 或 STL 工程件上会被规模击穿。

验证练习用 60 到 90 分钟完成：拿一个你熟悉的点到三角形最近点函数，外面包一层 AABB 下界剪枝。先在 1000 个 triangle 上比较直接遍历和剪枝遍历的候选 triangle 数，再把 triangle 数扩大到 10 万。预期结果不是一定得到最优速度，而是能看到候选数量从 `N` 级别下降到远小于 `N` 的数量级，并且最近距离与直接方法一致。

下一章自然会进入“从几何内核到完整几何处理管线”。因为单个查询加速只是第一步，真正的 CT mesh 修复、STL 检查和表面重建还需要把索引、局部更新、拓扑修复、误差度量和可视化验证串成可重复的 pipeline。
